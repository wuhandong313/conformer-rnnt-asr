1. 四个阶段总览

9 轮迭代可以分成四段：建立框架（把多头草拟变成一条严格的条件链）、 容量实验（结构 → 共享容量 → 逐头容量，最后证伪容量路线）、 流式预算（1 帧未来预算下重建复制电路，先败后胜）、 换轨显示（草稿不再参与解码，指标从接受率换成命中率 × 提前量）。

iter-1多头基线与消融定型

动机
验证"在冻结的 joiner 之上加零初始化残差头"这条路是否安全可用。
改动
joiner 之上加 K 个零初始化 Medusa 残差头（stream_local 上下文）；跑消融矩阵筛选。
结果
WINNER = stream_h2_kl0，h1=0.80 / h2=0.22。
教训
KL 出局。KL 项把草稿拉向 blank-dominant 的 base 分布，与 CE 目标直接冲突， 于是 kl_weight: 0 成为定局。零初始化 + 冻结 base 的安全模式同时成立。

iter-2 / 2b / 2c / 2d链式草拟 + lookahead 解除定型

动机
第 2 个头不知道该条件在什么上，接受率上不去。
改动
chain_states: true（head-k 条件于 teacher-forcing 滚动状态）+ draft_after_emit（post-emit 对齐）。probe_emit_gap.py 测出 lookahead=1 时 h1 的错误 60% 落在 gap=1、40% 落在 gap≥2（emit 帧不可见）→ 把 lookahead 解到 8。
结果
h1 显著提升，但随即撞上信息天花板；h2/h3 仍低。
教训
链式框架定型。但 lookahead=8 违反了流式 right_ctx 约束 （right_ctx=4 mel = 1 reduced 帧），iter-8 必须收回——这成了阶段 C 的全部矛盾。

iter-3draft-conditioned chain heads定型 · 基础

动机
用 LSTM 状态链把前一头的信息传下去，训练不稳。
改动
head-k（k≥2）额外消费前一头 draft 的 embedding；训练用前头 argmax（detach）， 推理用真实 draft。
结果
条件严格同构，取代了失败的 LSTM 状态链。
教训
train/infer 逐位同构是后续一切的基础。此后任何条件机制都必须先回答 "训练与推理是否逐位一致"——iter-8h2 的推理窗 bug 正是这条原则被违反的代价。

iter-4rolled language states突破

动机
头的语言侧状态是静态的，表达不了"如果前一个 token 是 X，下一个该是什么"。
改动
head-k 额外接收 rolled 语言状态（训练 tgt_enc[l+k-1]； 推理在已接受 draft 上滚动 predictor），零初始化投影注入。
结果
warm-start from iter-3 best → h1=0.9105 （全 test-clean，lossless 2619/2620），h2≈0.45 / h3≈0.10。
教训
语言状态滚动是 h1 破 0.91 的直接原因；h2/h3 仍然差，为阶段 B 埋下伏笔。

3. 阶段 B · 容量实验（iter-5 ~ iter-7）一次失败 + 一次证伪

h2 停在 ~0.68 之后，"是不是容量不够"成了最自然的假设。三个节点依次试了 结构（帧级 attention）、共享容量（深路径）、逐头容量（参数翻倍）， 最终把这条假设证伪。

iter-5窗口帧级 attention失败 · 已回滚

动机
让 rolled state 作为 query 去"看"声学窗的每一帧，而不是只看展平后的整窗。
改动
rolled state 作 query，对 (B,T,W,D) 声学窗做帧级 attention。
结果
训练不稳，greedy PER 0.07 → 0.50，输出被破坏 → 回滚（win_attn_enabled=False，模块仅为 checkpoint 兼容保留）。
教训
会触碰 verifier 路径数值的机制一律不做；additive-only。 这是全项目最重要的一条红线——它把后面所有方案都限制在"零初始化、step-0 bit-identical"的形态里。

iter-6共享容量扩容有效

动机
h2 卡在 ~0.68 十个 epoch，怀疑共享容量饱和。
改动
context_mlp_extra——与主路径平行的 3 层深路径，输出层零初始化 （step-0 与 iter-4 bit-identical），warm-start BEST_iter4.ckpt。
结果
h1=0.927 / h2=0.690 / h3=0.365，超 iter-4。途中经历 warm-start PER 瞬态并自愈 （monitor 为此加了标记）。
教训
零初始化扩容是安全的 warm-start 方式；warm-start 后的 PER 瞬态是正常现象， 会自愈，不要据此回滚。

iter-7逐头容量（6.3M → 13M）证伪

动机
如果瓶颈是共享容量饱和，那就给每个头独立容量。
改动
每头独立的 context_mlp_heads（3 层）+ chain_state_proj_heads； medusa 参数 6.3M → 13M（翻倍）；warm-start iter-6 best。
结果
h1=0.920 / h2=0.688 / h3=0.346 / overall=0.651，PER=0.0729 —— 与 iter-6 原地踏步。h3 对 oracle tail 也只有 0.383， 失败集中在 emit 距离 2–4 帧（接受率 0.37）。
教训
容量不是瓶颈。头缺的是"验证器会发射什么"的信息与计算结构，不是参数。 这个负结论直接决定了 iter-8 的方向（转向验证器前瞻），也避免了后续继续堆参数。
这一阶段的真正产出是一个约束：瓶颈被定位在"信息"而不是"容量"之后， 所有后续方案都必须回答同一个问题——我能给头什么它现在还看不到的信息？ iter-8 的答案是"验证器在自己状态上的逐步 argmax"，iter-9 的答案是"窗内可见的未来音频帧数"。
4. 阶段 C · 流式预算（iter-8 ~ iter-8h2）先败后胜 · 0.521 → 0.751

阶段 B 把"容量"证伪之后，剩下的假设只有一个：信息。可流式约束下每帧只允许 1 帧未来（right_ctx=4 mel ÷ stride 4 = 1 reduced 帧），而此前所有实验 都在用 lookahead=8 的非流式窗。这一阶段要在合法窗内重建那些能力——第一次没做到， 第二次做到了，而两次之间只差一个推理 bug 的修复。

iter-81 帧预算：验证器前瞻 + 时延分解未达标 · 舍弃

动机
把 lookahead 收回流式合法的 1 帧，同时用"验证器在自己状态上的逐步 argmax" 补回信息：头自己不会算"验证器会发射什么"，那就把验证器的 argmax 直接读给它。
改动
四项同时改：① 声学窗重排 [t−7..t−1, t, t+1]（用合法过去帧换掉非法未来帧， 保持 9 列宽度以便 warm-start）；② chain_sim——head-k 读真 joiner 在窗内对自己 rolled state 的逐步 argmax（token / 偏移 / 置信度，零初始化注入，训练时从 base_logits 网格 gather， 零额外 FLOPs）；③ delay_decompose 时延分类器；④ verifier_distillation_loss 软目标蒸馏。
诊断
先测天花板：sim 读出上限 h1=0.948 / h2=0.918 / h3=0.894 （覆盖率 0.966 / 0.939 / 0.918）→ 判定"天花板成立，1 帧预算几乎不亏"。
结果
训练停在 overall=0.521 （epoch16 / step44400；8a 冷启动 0.452 → 0.504 → 平台 0.50–0.51，8b 蒸馏 ×3 得 0.524， 直注 0.523 / 0.519），低于 iter-7 的 0.651 → 舍弃。
教训
三条，见下框。其中第二条改变了此后所有诊断的做法。
iter-8 的真正产出是三条负结论
  • ① 上限诊断的方法论错误：diag_rollout_ceiling.py 的扫描没有限窗 （用了全序列 enc），测出的 0.948 是"无约束 rollout 上限"，不是 1 帧窗上限—— 它把方案可行性的判断带偏了。天花板测量必须与部署可见窗一致。
  • ② 信息守恒：1 帧预算砍掉的 7 帧未来声学是真实损失。sim 只能恢复窗口内可解析的事件 （实测覆盖率 h1 85.7% / h2 45.0%），窗外的部分只能靠 LM 先验（条件命中 ~0.5）， 补不回隐路径从 8 帧未来获得的泛化。
  • ③ 直注查表对训练动态敏感：blank 行学出巨大反 blank 信号（范数 6.2）而真实 token 行 对角线 ≈0 —— 稠密网格上发射稀疏，复制梯度被稀释；改为 found-only 后行范数又涨到 20+ （复制与偏移混合）。隐路径复制电路学得慢的根因是两层冻结变换，不是监督不足。

bug a56ab42推理窗被二次锚定修复 · 旧数字作废

发现
推理时 _chain_shared_terms 对 spec_decode 已经建好的 (B,W,D) 窗又做了一次 _anchor_window(·, T=1)：past 列被清零、 当前列错取 enc[t−past]、lookahead 列被清零。头在推理时只见过单列声学， 而训练路径完全不受影响（bit-identical）。
影响
iter-8 全系的数字都是在坏推理路径上测的——0.521 不能作为判决， "信息守恒"结论随之存疑，必须用修复后的推理重测。

iter-8h2推理窗修复 + 2 头重训全程最好 0.751

动机
bug 修复后，"1 帧预算到底够不够用"这个问题第一次有了干净的测量条件。
改动
修 a56ab42 后重训：num_heads: 2（h3 依既定决策舍弃）、 ce_loss_weights [0.8, 0.64]、max_draft 2，其余沿用 iter-8 最终态 （accept_ce 3.0 / sim_bias found-only + 10× lr），warm-start 8b''' 重启点 （epoch01-step5200，warm-start 时自动丢弃 medusa_heads.2.*）。
结果
h1=0.889 / h2=0.612 / overall=0.751（epoch09 / step≈25500）， PER=0.0733，lossless_fail=0—— 同头数口径超过 iter-7，也是全程最高的 overall。
教训
数字对不上先查推理路径。iter-8 的三条教训里，①（诊断未限窗）是真的、 ③（直注通路）是真的，而 ②（信息守恒）被这次重测推翻——1 帧预算不是主要矛盾。 训练已在 2026-08-31 按用户指令停止，ckpt 与 log 留档。
图 3 · 1 帧预算下的两轮结果，仅比较前两头（matched-head，100 样本口径）。 iter-7 与 iter-8 是 3 头模型，iter-8h2 是 2 头模型。同样的路线、同样的配置， 只把推理窗从错误的单列改回真窗，h1 +4.8pt / h2 +11.8pt。
这一阶段的转折点：0.521 → 0.751 之间没有改任何结构，只修了一个推理 bug。 "实验失败"与"路径失败"必须分开——如果当时直接接受 0.521 的判决， 就不会有全程最好的 0.751，阶段 D 的换轨也就没有可用的权重基底。
5. 阶段 D · 换轨显示（iter-9）价值模型换轨

前三个阶段的指标只有一个：接受率——它衡量"能省多少解码步"，也就是提速。 换轨把目标整个换掉：草稿不再参与解码，只负责提前上屏，真实 token 到达时确认或替换， 解码回归纯贪心 RNNT。于是接受率作废，新指标是

value(head-k) = 命中率 × 平均提前量(ms) − 替换(闪烁)惩罚

iter-9投机显示 Speculative Display换轨

动机
用户提出：草稿的价值不一定在"省解码步"——真实 token 到达前先把草稿显示出来， 用户就能提前看到字。这不需要无损性论证，也不改 RTF：明示放弃真实提速。
口径
提前量以 reduced 帧计（1 帧 = 4 mel = 40 ms）；命中 = 草稿与随后真实 emit 的 token 相同；替换 = 上屏后被改写（感官闪烁）。命中与否不影响显示行为本身—— 草稿在草拟那一刻就上屏，将来猜错只是替换，显示机制永远不会因为猜错而失效； 命中率只进入评分。
产出
scripts/eval_display.py（两趟评估器：pass 1 纯贪心产出参考序列并快照每个 emit 点的 post-emit 状态，pass 2 在快照上草拟并与 target = u+1+j 对齐打分）、 configs/server_display.yaml、两套评估配置 display_iter7.yaml / display_iter8h2.yaml、 model_ckpt_tag() 的 tag_suffix 旋钮（参数相同但价值模型不同的 ckpt 不再同名，避免 monitor 缓存串档）、单页说明 docs/iter9-speculative-display.html。

诊断复制区的虚高 vs 预测区的 43%口径纠正

动机
此前把 found%（sim 扫描在可见窗内问到答案的比例）当成"头的上限" ——那量的是复制通道。头干两件事：① 照抄 sim 读出（复制区，头是多余的）； ② 答案在窗外时自己猜（预测区，这才是头的战场）。
结果
h1 复制区命中 99.79%（n=7175）、预测区 43.01%（n=1195）；h2 复制区 82.76%（n=3723）、 预测区 42.85%（n=4546）。两头在预测区完全相同—— h2 总命中低的唯一原因是它 55% 的时间落在预测区（h1 只有 14%），不是它笨。
结论
hit% ≈ 覆盖率 × ~100% + (1 − 覆盖率) × 43%。覆盖率由 lookahead 决定 （h1 85.7% / h2 45.0% @look=1），43% 是与头深度无关的常数—— 瓶颈钉死在"窗里能看到多少未来音频帧"。对照：配置 A 放宽到 8 帧，同一机制预测区 95.94% / 69.22%（43% → 96% / 69%）。
副产品
纯语言先验（_lm_free_run，声学固定为句级均值）在预测区只有 2.18% / 0.64%，且 84–98% 的时间直接弃权。 头高出先验 40+ 个点 → 头确实在拿声学窗外推，不是在当语言模型。

做法

结果

代价

估算式 hit% ≈ 覆盖率 × 1 + (1 − 覆盖率) × p_pred：覆盖率杠杆有配置 A 的实测支撑 （放宽到 8 帧 → 预测区 96% / 69%），确定性高得多；"提 43%" 目前只是假设。

换轨之后，问题第一次有了明确的两条边——左边界是窗口（覆盖率的物理上限）， 右边界是预测区那个 43%。三个杠杆里，"加长过去窗"零延迟、不需要动 base， 是唯一还没被实验碰过的方向；覆盖率杠杆确定但代价是系统延迟翻倍且要重训 base。
6. 关键教训 · 方法论8 条

把九个节点里的"下次该怎么做"抽出来，按对后续行为的影响力排序。 前四条是硬约束，后四条是判断纪律。

  1. 会触碰 verifier 路径数值的机制一律不做；additive-only。 iter-5 用一次真实事故换来这条：帧级 attention 打进 verifier 路径后 greedy PER 从 0.07 涨到 0.50， 输出被破坏。此后所有新模块必须零初始化、step-0 与基线 bit-identical。
  2. train/infer 逐位同构。 任何条件机制上线前先回答"训练与推理是否逐位一致"。iter-3 的 draft-conditioned 头建立了这个范式； iter-8h2 的推理窗 bug（_anchor_window 被二次调用）正是违反它的代价—— 训练路径完全正常，错误数字却跑完了整个阶段才被发现。
  3. 容量不是瓶颈。 iter-7 把 medusa 参数 6.3M → 13M 翻倍，h2 0.690 → 0.688、h3 0.365 → 0.346，原地踏步。 此后不再堆参数，一律先问"能给它什么现在看不到的信息"。
  4. 天花板测量必须与部署可见窗一致。 iter-8 的 diag_rollout_ceiling.py 用了全序列 enc，测出 0.948 的"无约束上限"， 而真实 1 帧窗的覆盖率只有 h1 85.7% / h2 45.0%。诊断条件 ≠ 部署条件时，数字会系统性偏乐观， 并直接误导方案的可行性判断。
  5. 先问"这个指标量的是什么"。 found% 量的是复制通道的上限，不是头的预测能力。口径纠正（区域拆分）之后才发现： h1 的 90% 是复制通道刷出来的虚高，两头在预测区其实都是 43%。指标的名字不等于它量到的东西。
  6. "实验失败" ≠ "路径失败"。 iter-8 的 0.521 坏在推理 bug 上；修复后同一条路线给出全程最好的 0.751。 在宣布一条路线死亡之前，先确认测量它的仪器是好的。
  7. 结论要跟着口径走，数字要跟着 ckpt 走。 两次踩坑：同宽不同义的窗（9 列，past=0/look=8 与 past=7/look=1）产出 47.91 / 14.81 的假基线； val-* 通配回退抓到别的迭代的 ckpt（strict 加载 11 个 unexpected 键）、 warm-start 过滤把共享 MLP 的层索引误判为头索引而丢弃（范数 97.9 的权重回落零初始化）。 修复：窗口语义写进评估配置、tag_suffix 与 ckpt 白名单、头键索引只在 per-head ModuleList 下读。
  8. 负结论与突破同样重要，必须留档。 三次舍弃（iter-5 回滚 / iter-7 证伪 / iter-8 未达标）决定了后面不再走哪条路—— 没有它们，iter-8h2 会重复容量实验，iter-9 会继续在提速指标上打转。
